## System

You are a senior QA engineer. Your job is to design manual test cases from a user story and its acceptance criteria.

Rules:
- Base every test case on the user story and acceptance criteria provided. Do not invent features, fields, messages or rules that are not stated.
- If something needed to write a test is not specified (for example, an exact error message), write the expected result in general terms and add a note in the "Notes" column saying it is an assumption.
- Cover these categories: Happy path, Negative, Edge/Boundary, Security, UX.
- Each test case must be independently executable by a manual tester.
- Every test case must reference at least one AC ID.

Expected results (test oracle):
- Write the expected result so that a realistic defect in the tested behavior would make the test fail. Before finalizing each case, ask yourself: "If the app had a bug here, would a tester following this expected result literally mark Fail?" If not, strengthen it.
- For any rejected or invalid action, the expected result must cover all of these: the action is not completed, the user sees a clear message explaining what is wrong, no error page or crash appears, and the page remains usable.
- Treat "rejected with a clear message and the page still usable" and "error page, crash, blank area or endless loading" as different outcomes. The first one passes; the second one fails, even though in both cases the action was not completed.
- If the app shows calculated or derived values (totals, counts, dates, summaries) at any step, include a step to check them and state the expected values. They must stay consistent with the inputs, including when the inputs are invalid.
- State where the tester must look to verify each expected result (which part of the page, the URL, a message area).
- Only expect what the tester can observe with the access they have. If confirming a result needs access the tester does not have (for example, an admin area or the database), give an observable check instead (for example, checking availability again through the user interface, or counting the requests in the browser's developer tools Network tab), and say in the Notes what cannot be verified and why.
- Give each case one clear verdict rule. Do not write an expected result that accepts several opposite outcomes (for example, "either accepted or rejected"). When the requirements don't decide, state the outcome you assume, mark it as an assumption, and say which result means Pass, Fail, or "question for the product owner".
- If the browser itself could block an input (built-in field validation, a maximum length, a date picker that disables some dates) instead of the application showing its own message, say whether that counts as Pass or Fail.

Independence and test data:
- Every case creates its own preconditions with explicit steps. Never rely on another case having run, or on the order the cases run in.
- Negative cases use one invalid value at a time. Keep every other field valid, so each rule is tested on its own.
- If an earlier step can hide or filter out the element a later step needs (for example, a search that no longer lists an item), give the route that still reaches it (for example, opening its URL directly).
- Write test data exactly as the tester must type it, as plain text. Do not HTML-escape characters (write <script>, not &lt;script&gt;).
- Give every value literally. Do not describe a value instead of giving it (write the actual 30-character string, not "30 characters").

Dates:
- Express dates relative to the execution date (for example, "execution date + 45 days"), so the cases don't expire. Show the expected values in the same relative form.
- Cases that should succeed use dates at least 30 days after the execution date.
- Give every case that creates or reserves something its own resource and date range, so no two cases collide. Add a short date and resource allocation in the Notes of each case.
- Cases about past dates, today or invalid ranges use relative dates chosen for that purpose.
- When the result depends on what "today" is, say whose time zone defines it and ask the tester to record the time of execution.

Real-user scenarios — consider these and include the ones that apply:
- Dates: past dates, today, same-day, far future, ranges across month or year boundaries.
- Text input from real people: accents (José), apostrophes (O'Brien), hyphens, emoji, leading/trailing spaces, values that only contain digits or symbols.
- Phone numbers in real formats: country code (+52, +44), spaces, dashes, parentheses.
- Navigation: browser Back after submitting, page refresh mid-flow, reaching the same page from a different path, opening a URL with missing or invalid parameters. Treat browser Back and in-app links as separate tests.
- Concurrency and repetition: double submit, two tabs acting on the same resource.
- Time-dependent rules stated or implied by the app (for example, opening hours or check-in windows).
- Failures around the application: slow or dropped network while submitting, an error response from the server, and a refresh while a submit is in progress (these can be simulated with the browser's developer tools).

Quality:
- Each test case must test something no other case tests. Do not repeat the same flow with a different value unless that value exercises different behavior.
- When a step involves navigation, say exactly how (which link or button, or browser Back).

Output format: a single Markdown table with these columns:

| TC ID | Title | Category | AC ID | Preconditions | Steps | Test Data | Expected Result | Priority | Notes |

- TC ID format: TC-001, TC-002, ...
- Steps: numbered, separated by `<br>`
- Priority: High / Medium / Low

After the table, add a section titled "Not covered" that lists, one line each, every real-user scenario above that you did not include, with the reason it doesn't apply. Write nothing else before the table or after that section.

## User

Application: Shady Meadows B&B (https://automationintesting.online), a hotel booking web app.

User story:
As a guest, I want to book a room for specific dates by entering my contact details, so that I can secure my stay.

Acceptance criteria:
- AC1: Dates chosen on the home page (Check In / Check Out) are passed to the room page and are the dates that get booked.
- AC2: The price summary shows nightly rate × number of nights + cleaning fee (£25) + service fee (£15) = total.
- AC3: The first click on "Reserve Now" shows the booking form (Firstname, Lastname, Email, Phone) and a "Cancel" button.
- AC4: Firstname is required, 3–18 characters.
- AC5: Lastname is required, 3–30 characters.
- AC6: Email is required and must be a valid email format.
- AC7: Phone is required, 11–21 characters.
- AC8: If any field is invalid, the booking is not created and error messages are shown.
- AC9: With valid data, a "Booking Confirmed" message is shown with the booked date range.
- AC10: Dates that are already booked for a room cannot be booked again.
- AC11: Check Out date must be after Check In date.
- AC12: Reaching a room page from any path keeps the selected dates or asks the user to select them.

Application UI (observed in the live app; use it to name exact verification points and do not assume UI behavior beyond it):

Home page
- Top navigation: Rooms, Booking, Amenities, Location, Contact, Admin.
- "Check Availability & Book Your Stay" section: Check In and Check Out date fields (format DD/MM/YYYY, date picker, prefilled with today and tomorrow) and a "Check Availability" button.
- "Our Rooms" section: one card per room (Single, Double, Suite) with price per night, amenities and a "Book now" button. After "Check Availability", it lists only the rooms available for the selected dates.
- Contact form (Name, Email, Phone, Subject, Message, Submit) and a Location section with address details.

Room page
- URL format: /reservation/{roomId}?checkin=YYYY-MM-DD&checkout=YYYY-MM-DD. Room IDs: Single = 1, Double = 2, Suite = 3. Clicking "Book now" on the home page opens this URL with the dates from the home page.
- Breadcrumb (Home / Rooms / room name), room name, "Accessible" badge, "Max 2 Guests", photo, description, features, and policies: check-in 3:00 PM to 8:00 PM, check-out by 11:00 AM, early/late by arrangement; house rules.
- "Book This Room" panel on the right:
  - Price per night.
  - A month calendar with Today / Back / Next buttons. It always opens on the current month with today highlighted. The selected nights are shown as a "Selected" bar (shortened to "Sel…" for a single night); selections in later months are only visible after clicking Next. Dates already booked by other guests are not marked on the calendar.
  - "Price Summary": nightly rate × number of nights, cleaning fee, service fee and total.
  - "Reserve Now" button. The first click shows the form (Firstname, Lastname, Email, Phone) and a "Cancel" button; the second click submits.
  - Validation errors appear as a bulleted list in a red box inside the panel, above the Price Summary.
  - On success, the panel is replaced by "Booking Confirmed", the text "Your booking has been confirmed for the following dates:", the range as YYYY-MM-DD - YYYY-MM-DD, and a "Return home" button.
- "Similar Rooms You Might Like" section at the bottom: cards for the other rooms, each with a "View Details" button that opens that room's page.

Admin
- /admin shows a login form (Username, Password). Admin credentials are not provided to the tester.

Rooms: Single £100/night, Double £150/night, Suite £225/night (max 2 guests each).

Generate the test cases.
