## Verdict rules

- **Pass**: the application behaves as the acceptance criteria require. For a rejected action, all three must hold: the action is not completed, a clear message is shown, and the page stays usable.
- **Fail**: the application breaks a rule that an acceptance criterion states, or shows an error page, a crash, a blank area or endless loading (no response after 30 seconds without throttling). A behavior that an AC requires but that is missing is Fail.
- **Blocked**: the case can't be run for a reason outside the application's behavior. Examples: the site or DevTools is unavailable, or the availability check in a case's Preconditions does not list the room for that case's range (another user of this shared public demo has booked it). When a case is Blocked by taken dates, the tester may shift all of that case's dates by the same number of days, keep success dates at D+30 or later, record the new dates, and re-run.
- **Question**: the behavior is not covered by any AC. Never use Question for something an AC requires.
- **Input the browser or page blocks before submission** (native validation bubble, a maximum length that stops typing, a disabled date in a date picker, a date field that refuses or auto-corrects a value): the rule counts as enforced. The case is **Pass** if nothing is submitted, the bubble, disabled date or refusal is visible to the tester, and the page stays usable. If a value is cut or auto-corrected to a valid value, the tester records what the field now holds and does not submit it. That outcome is also **Pass**. If a value that an AC allows is cut or blocked (for example, an 18-character Firstname cut to 17), that is **Fail**.
- **Values that meet AC4–AC7 are valid data, and AC9 requires them to be accepted.** If such a value is rejected with a clear message that cites a content rule no AC states (for example, "letters only"), the verdict is **Question**. If it is rejected with no message, or with a message that contradicts the ACs (for example, "too short" for a 3-character Firstname), the verdict is **Fail**.
- **AC12 has two acceptable outcomes:** the room page keeps the selected dates, or it asks the user to select dates. Either one is Pass. Showing or booking a different range without asking is Fail.
- **Message wording** is not specified anywhere. A message passes if it appears where the case says (the red error box in "Book This Room", above Price Summary, or the browser's bubble under the rule above) and it names the field or date problem.
- **Dates:** D is the execution date on the tester's device, in that device's local time zone. That time zone defines "today" for this suite, which is an assumption. D+n means D plus n days. In a URL or in the confirmation text, `<D+n>` stands for that date written as YYYY-MM-DD. In the home page fields, type it as DD/MM/YYYY. At the start of every run, record the date, the time and the time zone.
- **Availability check (room R, range A→B):** open a new tab at https://automationintesting.online. In "Check Availability & Book Your Stay", type Check In = A and Check Out = B, then click "Check Availability". In the "Our Rooms" section, record whether R is listed. This is the observable proof that a booking exists, because the tester has no admin access.
- **Network evidence:** in the DevTools Network tab, turn on "Preserve log" and filter by Fetch/XHR. The "booking request" is the POST request sent when the second click on "Reserve Now" submits the form.

## Not covered

- Error response from the server (for example, HTTP 500): the tester can't produce one. Chrome DevTools can throttle or cut off a request (TC-032, TC-039, TC-040), but it can't make the server answer the booking request with an error status without a proxy tool, which is outside the tester's access.
- Time-dependent rules (check-in 3:00–8:00 PM, check-out by 11:00 AM): the booking form has no time field, and no AC ties booking to these hours. Only the date-level "today" behavior is exercised, in TC-028, where the time is recorded for information.
