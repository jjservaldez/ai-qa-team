## Verdict rules

**Verdicts (apply to every case)**
- **Pass:** the application behaves as the acceptance criteria require. For a rejected action, that means the action is not completed, a clear message is shown, and the page stays usable.
- **Fail:** the application breaks a rule that an acceptance criterion states, or it shows an error page, a crash, a blank area or endless loading.
- **Blocked:** the case can't be executed for a reason outside the application's behavior. Examples: the site is unreachable, or the precondition AVAIL check does not list the room because someone else on this shared demo has already taken those dates.
- **Question:** the behavior is not covered by any acceptance criterion. A required behavior that is missing is Fail, never Question.

**Suite decisions**
1. **Input the browser blocks:** if the browser stops an invalid value before the app receives it (a native "required" or email bubble, or a date picker that refuses a date), that bubble or refusal counts as the clear message (R2), and every other check still applies. If a maxlength limit cuts a typed value down to a valid one, or the date picker corrects the range by itself, record the stored value and do not submit it. That check is Pass, because the invalid value cannot reach the app.
2. **Valid data:** a value that meets AC4–AC7 as written (present, within the length range, valid email format) is valid. Rejecting such a value, for example because of accents, emoji, digits or symbols, is Fail under AC9.
3. **Behavior no AC covers:** past dates, same-day check-in, a booking horizon, back-to-back stays, whitespace-only names, unknown room IDs, and feedback when the network fails. A case on one of these states an assumed expected result. If the app behaves differently but cleanly (a clear message or a clean acceptance, and the page stays usable), the verdict is Question. An error page, crash, blank area or endless loading is Fail.
4. **Endless loading:** no visible result after 10 s, or after 60 s in cases that throttle the network.
5. **Today:** the calendar date on the tester's device, in the device's time zone. The browser uses it for the home page's prefilled dates and for the calendar highlight (assumption). Record the execution date, time and time zone for every case.

**Shared notation used in the cases**
- **D+n / D−n:** the execution date plus or minus n days. On the home page, type it as DD/MM/YYYY. In URLs and in the confirmation, it appears as YYYY-MM-DD.
- **V:** Firstname `Maria`, Lastname `Lopez`, Email `maria.lopez@example.com`, Phone `+441234567890`.
- **V2:** Firstname `Carlos`, Lastname `Ramirez`, Email `carlos.ramirez@example.com`, Phone `+525512345678`.
- **NET:** Chrome DevTools open on the Network tab, with "Preserve log" on and throttling set to "No throttling".
- **Booking request:** the request sent by the second Reserve Now click. This assumes a POST whose URL contains "booking"; if it is named differently, identify it by its timing.
- **Open room URL:** type `https://automationintesting.online/reservation/{id}?checkin={in}&checkout={out}` in the address bar and press Enter. Room IDs: Single = 1, Double = 2, Suite = 3.
- **AVAIL(room, in, out):** open `https://automationintesting.online/` in a new tab, type the dates into Check In and Check Out, click Check Availability, then look in "Our Rooms" for that room's card. "Lists" means the card is shown.
- **CONF(in - out):** check all of these:
  - The Book This Room panel is replaced by "Booking Confirmed", the text "Your booking has been confirmed for the following dates:", the range `in - out` in YYYY-MM-DD, and a "Return home" button.
  - The booking request has a 2xx status.
  - A final AVAIL check for the same room and dates no longer lists the room.
- **R (rejection checks):**
  - R1: the panel does not show "Booking Confirmed".
  - R2: a red box above the Price Summary lists a message that names the wrong field or rule, and lists no error for fields that hold valid values.
  - R3: no error page, crash, blank panel or endless loading.
  - R4: the form fields can still be edited and Reserve Now still responds.
  - R5: the booking request is either absent or has a non-2xx status.
  - R6: the Price Summary still shows the values stated in the case.
  - R7: AVAIL for the case's room and dates still lists the room.

## Not covered

- Server error response (5xx): Chrome DevTools can block a request or go offline (TC-036), but it cannot make this server return a 5xx without a proxy, which the tester doesn't have. The 4xx responses are covered by the validation and AC10 cases.
- Time-dependent rules (check-in 3:00–8:00 PM, check-out by 11:00 AM): these are stated as arrival and departure policies, and neither the acceptance criteria nor the observed UI uses them to restrict booking. TC-017 only records the execution time.
