### 2. Suite-level findings

**Coverage gaps**
- **AC10, other rooms (applies).** No case checks that a booking on the Single for D to D+2 does not block the Double or Suite for the same dates.
- **AC10, other overlap shapes (applies).** No case books a range that fully contains an existing booking, and none ends on the existing booking's Check In day (the mirror of TC-027).
- **AC11 by URL (applies).** Checkout <= checkin is only tried from the home page. The room URL accepts dates directly (UI map line 10).
- **AC12, other paths (applies).** "View Details" on Similar Rooms, the breadcrumb and the top nav are not covered (UI map lines 4, 11, 19).
- **AC7, characters (applies).** The ACs count characters, not digits. No case uses "+", spaces or letters, e.g. "+44 7700 900123" or letters at a valid length.
- **AC6, valid edge formats (applies).** Only obviously invalid emails are tested. There are no valid edge formats (plus addressing, subdomains) and no borderline ones such as john@example with no TLD. Whether those count as valid must be marked as an assumption.
- **Past dates (applies).** No case books a Check In in the past, by date picker or by URL. The ACs are silent, so this would be an assumption case.
- **Server-side length limits (applies).** TC-035 covers only part of AC4, AC6 and AC7. The Lastname limits and the maximum lengths are never checked on the server.

**Conditions the suite ignores**
- **Slow or dropped network (applies).** Submit with DevTools throttling or offline. There is no expectation for a hung submit or a retry that creates a duplicate.
- **Backend errors (applies).** No case defines what the panel shows when the booking API fails. This is also why the weak oracles in TC-014 to TC-017 matter.
- **Time of day and time zones (applies).** The fields are prefilled with "today" (UI map line 5), and the dates change format between home (DD/MM/YYYY), URL and confirmation (YYYY-MM-DD). A UTC conversion can shift a date by one. No case runs near midnight or in a non-UK time zone.
- **Two sessions, same data (applies).** The calendar doesn't show booked dates, so two browsers can both open the same room and dates and submit. No case checks that exactly one succeeds. The shared public demo also means other people's bookings can break preconditions.
- **Refresh or Back during and after submit (applies).** TC-031 covers reload before submit only. No case covers browser Back after "Booking Confirmed" and resubmitting, or refreshing mid-submit.
- **Data that looks valid but isn't (applies).** No case uses an apostrophe (O'Brien), accents (José, Müller), emoji at a length boundary (emoji count as 2 UTF-16 units), leading or trailing spaces on a valid name, or a very long paste (e.g. 1,000 characters) beyond the +1 boundary.
- **Verifying "no booking created" (applies).** No admin access (UI map line 22). Every negative case can only check that "Booking Confirmed" is absent; the suite should say so explicitly.
